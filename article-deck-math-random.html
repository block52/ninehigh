Our “Cryptographic” Deck Used Math.random(): Four Bugs in @block52/deck

By Nine High Studios · October 2026 · 6 min read
Security Provably Fair Open Source

Our deck library said it shuffled with cryptographic randomness. It shuffled with Math.random(). We found that out while getting ready to recommend it to another poker engine, which is the worst possible moment to find it, and the best one too. This is what was wrong with @block52/deck 1.0.0, why each problem matters at a real-money table, and what changed in 1.1.0.

How we found it

We'd just written scenario tests for an open-source TypeScript poker engine, poker-engine-ts, and it has no deck class. Its live path takes the deck from the host application, which is the right design. So the natural suggestion was "here's ours". Before suggesting it, we read it again, line by line, the way we'd read someone else's. Four problems came out of that.

1. The "cryptographic" shuffle used Math.random()

Called without a seed, shuffle() built its own seed like this:

seed = Array.from({ length: 52 }, () => Math.floor(1000000 * Math.random()));

Math.random() is fast and fine for animations. It is not a source of secrets. In V8 it's xorshift128+, with 128 bits of state, and its output can be predicted from enough earlier output. A 52-card deck has 52! orders, about 2225.6. A generator with 128 bits of state can reach only a vanishing fraction of them, and anyone who can model the generator can narrow down which ones.

The README said "cryptographic shuffling". Our own write-up about the library said it used Node's crypto.randomInt, and criticised other deck libraries for using Math.random(). The code did exactly what we were criticising.

Why this matters at a poker table: if a shuffle's randomness can be predicted, so can the cards. That's the one property a deck must have, and the one that's hardest to notice is missing, because a predictable shuffle looks exactly as random as a good one.

2. Modulo bias

The shuffle itself was Fisher-Yates, which is correct, but it picked each swap index as seed[i] % (i + 1), with seed[i] drawn from 0 to 999,999. Unless i + 1 divides 1,000,000 exactly, some remainders come up one more time than others. For position 51 (52 choices), 1,000,000 = 52 × 19,230 + 40, so the first 40 swap targets are each slightly more likely than the last 12. The bias is small, but it's systematic, and a fair deck shouldn't have one at all.

3. deal(n) skipped cards

public deal(amount: number): Card[] { this.top += amount; // advance first... return Array.from({ length: amount }, () => this.getNext()); // ...then advance again }

deal(5) moved the deck forward five cards and then drew five more. It returned cards 6 to 10 and left the next draw at card 11. The existing test only checked that five cards came back, never which five.

4. It only ran in Node

The library imported createHash from Node's crypto module. Fine for a server, but it can't run in a browser or an edge runtime. poker-engine-ts runs the same code in all three, so a Node-only deck would have broken the property it cares about most.

The fix, in 1.1.0

  • Secure randomness. Unseeded shuffles draw from Web Crypto getRandomValues, which is built into Node 20+, every browser, and edge runtimes. If it's missing, the shuffle throws. There's no fallback to Math.random(), ever.
  • No bias. Each swap index is drawn uniformly from [0, i] by rejection sampling. Any 32-bit value that would make the remainder uneven is thrown away and redrawn.
  • Portable. The package ships its own SHA-256, about 70 lines of TypeScript checked against the official FIPS 180-4 test vectors and against Node's implementation for inputs of every padding length. It imports nothing from Node and still has zero dependencies.
  • deal(n) deals the next n cards, and throws if there aren't that many left.
  • Interoperable notation. fromString now reads T for ten and lower-case suits. toMnemonics({ tens: "T", suitCase: "lower" }) writes the order as As, Td, …, the format other engines expect.

Nothing that was correct changed. A given seed produces exactly the same order and seed hash as in 1.0.0, so recorded hands still replay, and deck hashes are identical. A test pins both against the 1.0.0 algorithm.

How we test a shuffle

You can't unit-test randomness by looking at one shuffle, so the suite tests the properties instead:

  • No Math.random(). The test replaces it with a function that throws, then shuffles. If anything calls it, the test fails.
  • No silent fallback. With Web Crypto removed, the shuffle must throw.
  • Rejection works. A fake random source feeds the one biased value first and checks it's discarded.
  • Uniform positions. 26,000 shuffles, tracking where three cards land across all 52 positions, with a chi-square test at p = 0.0001. A biased shuffle fails it; a fair one passes.

The suite went from 17 tests to 33, and it runs on Node 20, 22 and 24.

What we took from it

The code wasn't the only thing wrong: our documentation described the code we meant to write, not the code we wrote. Nobody had compared the claim with the implementation, because the claim was ours. Re-reading our own library as if it were someone else's found more in an hour than a year of using it had.

@block52/deck is MIT-licensed. If you used 1.0.0 to shuffle anything that matters, upgrade to 1.1.0.
